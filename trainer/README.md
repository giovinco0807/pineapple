# OFC トレーナー（レギュラー）

https://ofc.olegsolvers.com/ を参考にした、レギュラーOFC Pineapple（ヘッズアップ・Jokerなし）のローカル学習用Webアプリ。

## 機能

- **トレーニング**: AI相手に1ハンドずつプレイ。各判断を全候補のEVランキングで採点。
  - 最善手なら自動続行 / 最善手を強制 / 候補1つの時はスキップ
  - しきい値以上のEVロスは自動でミス記録
- **エディタ**: 任意の局面（自分・相手の盤面、配札、死札）を作って候補EVランキングを表示
- **ハンド入力**: 実戦・動画のハンドを1つ丸ごと（両席・全5ストリート）書き起こして一括採点
- **ミス復習**: 記録されたミスを同じ局面でリトライ
- **アカウント**: ヘッダーのセレクタで履歴を切り替え。ハンド履歴・ミス・統計はすべてアカウント単位。

## アカウント

ローカル専用ツールなのでログインではなく「名前付きの履歴バケツ」。

- ヘッダーの `＋` で作成、セレクタで切り替え、`🗑` でそのアカウントの履歴を全削除
- 選択中のIDはブラウザの localStorage に保存され、全APIに `X-Account-Id` ヘッダーで乗る
- ヘッダーが無い／未知のIDの場合は `default` アカウントにフォールバック（認証ではなく識別）
- アカウント導入前のDBは起動時に自動マイグレーションされ、既存の行は `default` に紐づく
- ハンドは**開始時**のアカウントに記録される（途中で切り替えても記録先は変わらない）
- `default` アカウントは削除不可

## 起動

```powershell
cd regular-ofc-pineapple
python -m uvicorn trainer.app:app --host 127.0.0.1 --port 8093
```

ブラウザで http://127.0.0.1:8093 を開く。

## 構成

- `app.py` — FastAPI（認証なし・ローカル用）
- `game.py` — トレーニングセッション（配札、AI対戦相手、バックグラウンドEV解析、採点）
- `evaluator.py` — ストリート別評価器（候補列挙 + EVランキング）
- `fl_ev.py` — FL EV定数を `configs/` から読む（ハードコード禁止）
- `store.py` — SQLite（アカウント・ミス・ハンド履歴、`trainer/data/trainer.sqlite3`）
  - `GET /api/accounts` / `POST /api/accounts` / `DELETE /api/accounts/{id}`
  - `GET /api/history?limit=N` — アカウントのハンド履歴
- `static/` — フロントエンド（素のJS・日本語UI）

## ハンド入力（実戦ハンドの採点）

`handlog.py` + `static/handlog.js`。動画や実戦のハンドを書き起こして、あとから全判断を採点する。

- **入力順は配り順に固定**（5ストリート × 2席 = 10手番）。どちらの盤面か・どの街かをアプリが決めるので、
  手書き記録にありがちな取り違えが起きない
- カードはピッカーのクリック、またはキーボード（`a`→`s` で A♠、置き場所は `t`/`m`/`b`、捨ては `x`、`⌫` で1つ戻す）
- **席によって入力枚数が違う**。自分は配札3枚を入力して2枚置き、残り1枚が自動で捨て札になる。
  相手は**置いた2枚だけ**（レギュラーでは相手の捨て札は見えないため）
- 相手の捨て札は10手番のあとの**11ステップ目**でまとめて入力（任意）。分かる街だけでよい。
  枠をクリックか `↑`/`↓` で入力先の街を移動する（数字キーは使わない — 2/3/4 はランクなので取り合いになる）
- 保存したハンドは一覧から複数選択して一括解析（バックグラウンドジョブ＋進捗ポーリング）
- 「相手の判断も採点」で相手側も採点する。**捨て札が入力されていない街はスキップ**する
  （相手のT0は5枚とも見えているので、捨て札が1枚もなくても採点できる）

局面の復元はハンド記録から機械的に導出される:

| 対象 | 復元規則 |
|------|---------|
| 相手盤面 | 同じ街で自分が先行なら相手の当街配置は**含まない**、後攻なら**含む** |
| 死札 | 自分の捨て札のみ（相手の捨て札はレギュラーでは非公開） |
| 手番 | `hero_position` と街内の順序から `first`/`second` を決定 |
| 相手の配札 | 「置いた札 + 捨て札（分かっていれば）」から導出。2枚なら未確定＝その街は採点対象外 |

**自分の採点は相手の捨て札の有無に一切影響されない**。相手の捨て札はそもそもヒーローの情報集合に
入っていないため、`dead` にも入らない。実測でも同一ハンドの自分T0が捨て札の有無で同じ順位・同じEVロスになる。

API: `POST /api/handlog`（保存）/ `PUT /api/handlog/{id}` / `GET /api/handlog` / `POST /api/handlog/analyze` →
`GET /api/handlog/job/{job_id}` で進捗。解析結果はハンド行に保存され、再オープン時は再計算しない。

### ファンタジーランドのハンド（2026-08-13 追加）

ヘッダーの「種類」で 通常 / 自分がFL / 相手がFL / 両者FL を選ぶ。FLの席は**街を打たない**ので、
入力ステップの数と順番が変わる（FLの席は13枚セットの1手番、通常の席は5街ぶん）:

| 種類 | 入力ステップ | 採点できるもの |
|------|------------|--------------|
| 通常 | 10（5街×2席） | 全判断（エンジン） |
| 自分がFL | 6（自分のFL + 相手の5街） | **自分のFLセット**（全数え上げ） |
| 相手がFL | 6（相手のFL + 自分の5街） | 相手のFLセット（14枚目が分かる場合） |
| 両者FL | 2 | 双方のFLセット |

- 自分は配られた**14枚**を入力して13枚を置く（残り1枚は自動で捨て札）。相手は見えている**13枚**だけ。
  相手が伏せた14枚目は、通常ハンドの捨て札と同じ最後のパネルで任意入力
- **相手がFLの局面は自分の街をほぼ採点できない**。m3エンジンの隠しカード信念サンプラー
  （`hu_belief._validate_decision_observation`）が通常の相手の盤面しか受け付けず、
  `expected hero/opponent/hero-discards/opponent-discards=(7,7,1,1), got (7,0,1,0)` で拒否する。
  MCフォールバックは相手に通常の5街を打たせてしまい「粗い答え」ではなく**別の相手への答え**になるので、
  黙って落とさず採点対象から外す（`vs_fl_ungraded` として結果に表示）
  - **例外はT0先行のみ**。この1ノードだけ vs-FL と通常のジオメトリが両方 (0,0,5,0) で一致するため
    リクエストが通り、通常のT0先行モデルが答える。**そのモデルはFLを知らない**（実測でも順位が変わるのは
    フィンガープリント経由でシードが変わるだけ）。`configs/fl_ev_regular_v4_selfplay.json` の
    `provenance/m11_vsfl_models/t0_vs_fl` に「既知の近似」として記録済みの経路なので、
    ハンド最大の判断を捨てずに **近似として採点し `vs_fl_approx` で明示**する（結果表では順位に ※）
  - T0後攻は vs-FL も通常もジオメトリが合わず拒否される
  - 本来の vs-FL ランカーは別クレートに存在する: `rust/fl_solver_regular` + `weights/vsfl/vsfl_t{0,1,2,3}_v*.vfl1`。
    m3エンジンはこの形式をロードできないので、街の採点をちゃんとやるならここを繋ぐ
- FLセットの採点は `trainer/fl_grade.py`。14枚から作れる**全合法配置（約33万通り）を数え上げ**、
  ロイヤリティ＋ステイ価値（`FL_EV_14`=9.6）で順位付けする。1ハンド約8〜10秒
  - 相手の14枚目が不明なときは「既知の13枚の並べ方」だけを順位付けし、そう明示する（別の問い）
  - **バーストしたセットは合法配置の列挙に無いので「見つからない」ではなく0点として扱う**（最善との差＝丸損）
  - 単位は街のEVロス（点/ハンド）と**違う**ので、結果表ではその旨をツールチップに出す
- 終局スコアは、FLだった席には**ステイ条件**（トップにスリーカード or ボトムにフォーカード以上）を、
  通常の席には**エントリー条件**（QQ+ かトリップス）を適用する

## 採点方法：モデル（既定）と教師探索

**2026-08-13 に既定を教師探索からモデルに切り替えた。** 根拠は `docs/trainer_ranking_quality_20260808.md`
の実測: 教師探索のT0ランキングは**シード支配**で、同一ハンドを5シードで回すと**5シードとも違う手が1位**、
手ごとのスコア差は平均25.87点（1ハンドが±40点で決まるゲームで）。同§2aでは「top10に絞って256世界まで
上げても収束しなかった（1ランキング357秒）」。

| | モデル（`method="model"`） | 教師探索（`method="teacher"`） |
|---|---|---|
| 何をする | 街の学習済みモデルが全合法手を1回のforward passで採点 | 全候補を標本世界でロールアウト |
| 決定性 | **あり**（同じ局面＝同じ順位・同じEV差） | なし（シード依存） |
| 1ハンド（自分の5判断） | **約1秒** | 41秒（fast）／約90秒（deep） |
| エンジン | `model_scores`（T0〜T3）＋ T4は従来の完全列挙 | `t0`〜`t4` |

UIは3画面（トレーニング／エディタ／ハンド入力）に「採点方法」セレクタがある。既定はモデル。
モデル選択時は**精度セレクタを無効化**する（モデルは粒子を1つも使わないので意味がないため）。

実測比較（ハンド#2・自分の5判断）:

| 街 | モデル | 教師探索(fast) |
|---|---|---|
| T0 | **1/232**（EVロス0） | 232/232（EVロス31.6） |
| T1 | 4/27（0.93） | 6/27（12.6） |
| T2 | **1/27**（0） | 24/27（6.0） |
| T3 | 3/21（0.04） | 20/21（0） |
| 合計 | **0.97** | 50.20 |

**エンジンDLLを差し替えた（2026-08-13）**。`model_scores` リクエスト種別は同梱の 2026-08-07 ビルドに
入っておらず `unsupported M3 request kind` で拒否されたため、現ソースから再ビルドしたものを
`target/release/ofc_hu_m3_engine.dll` に配置。旧DLLは同じ場所に `ofc_hu_m3_engine.20260807-backup.dll`
として保存してある。**教師出力は新旧で完全一致**を確認済み（ハンド#2の T0=232候補 / T1=27 / T2=27 /
T3=21、順序・スコアともビット一致）。

**エンジン側のバグを1件修正した（`search.rs` の `model_scores`）**。T0後攻だけが共通アームに落ちていて
`generate_turn_actions_trusted`（3枚から2枚）を呼んでおり、空盤面に2枚置いた候補を特徴量エンコーダが
`free outlook expects a board with two, four, six or eight open slots, got [1, 5, 5]` で拒否 →
**T0後攻の採点が黙ってMCフォールバックに落ちていた**（＝ヒーローが後攻のハンドすべて）。
T0は開始ジェネレータ（5枚一括）を使う唯一の街で、`decide` 側の `learned_t0_second_action` は
最初から `generate_initial_actions` を使っている。それに合わせた。外から見えない不具合だったので
`tests/test_trainer_model_grading.py::test_t0_second_seat_is_graded_by_the_model` で固定。

## 評価の仕組み（教師探索）

各ストリートの全合法手を列挙し、EVで降順ランキング。ユーザーの手の順位とベストとのEV差で採点する。

**採点に使うスコアはストリートごとに違う**（2026-08-13 修正）。エンジンは各手を2回スコアリングする
（選択用の candidate バッチと評価用の evaluation バッチ）が、返ってくる `sorted_index` がどちらの順序かは
街によって異なる（`rust/hu_m3_engine/src/search.rs`）:

| ストリート | 並び順の元 | JSONフィールド |
|-----------|-----------|---------------|
| T0 | selection_order（candidateバッチ） | `candidate_score` |
| T1 / T2 | evaluation_order | `score`（= `ev`） |
| T3 / T4 | candidateバッチ | `selection_score` |

`rank_score` はこの表に従って選ぶ。**順位と別のスコアでEV差を出すと矛盾する**: 実測で T1 の5位の手が
「EVロス 0＝best」と表示されていた。なお T0 は `ev` に切り替えられない（段階探索で枝刈りされた行は
少ないパーティクル数で測られており、行間で比較できない）。3ハンド×両席×全10判断＝60局面で
`sorted_index` 順と `rank_score` の単調性が一致することを確認済み。

### 精度と「同率」

サンプル数が少ないとスコアが粗くなり、**別の手が同点になる**。実測（1局面あたり・n=候補数、uniq=異なるスコアの数）:

| 精度 | T1先行 | T1後攻 | T2先行 | T2後攻 | T3先行 |
|------|--------|--------|--------|--------|--------|
| fast | 1.3秒 6/27 | 0.9秒 3/24 | 0.3秒 4/12 | 0.2秒 **1/9** | 0.1秒 3/12 |
| standard | 1.1秒 6/27 | 0.8秒 3/24 | 1.0秒 5/12 | 0.6秒 3/9 | 0.9秒 7/12 |
| deep | 21.7秒 22/27 | 12.5秒 20/24 | 4.7秒 8/12 | 2.1秒 9/9 | 1.9秒 10/12 |

`fast` の T2後攻は9候補すべてが同点＝採点不能だった。`standard` でも T0/T1 は 1サンプルのままなので
（`SAMPLES` 参照）ここは `fast` と同じ粗さになる。**記録済みハンドの採点には `deep`** を使うこと。

T0（実測、232候補）:

| サンプル | 先行 | 後攻 | 異なるスコア数（先行 / 後攻） |
|---------|------|------|---------------------------|
| (1,1,1) — fast/standard/high/deep | 40秒 | 15秒 | 20 / 29 |
| (2,4,1) — `deep_t0` | 330秒 | 59秒 | 41 / 60 |

T0を精査するかどうかは8倍の待ち時間との取引なので、既定にはせず `deep_t0` として選べるようにしてある。

ハンド1つ（自分だけ5判断・毎街先行）で `deep` は約90秒、15ハンドで約20分。
`deep_t0` は1ハンド約6分＝15ハンドで1.5時間。相手も採点するとそれぞれほぼ倍。
（いずれも他プロセスが16並列で回っている状態での実測なので、空いていればもっと速い）

### T3の順位は `ev` で付ける（2026-08-15）

上の表の「T3/T4 → `selection_score`（candidateバッチ）」のうち、**T3を `ev` に変更**した。
理由は実測: 1局面を固定して `evaluation_samples` を 1024→8192→32768 と上げると、
`selection_score` の上位2手の差は +2.875 → +7.325 → +6.950 と暴れ、`candidate_samples` を
8→512 にしても +7.325 → +4.438 と動く。一方 `ev` は +4.78/+4.99/+4.92、+4.99/+5.00/+4.93 で収束する。
**収束しない値で順位を付けていたので、同じ局面の判定がシードで変わっていた**
（実測: 1ハンドで8シード中4種類の最善手）。

- T0は `candidate_score` のまま。段階探索で枝刈りされた行は少ない粒子で測られており、
  行間で `ev` を比較できない（既存の理由がそのまま生きている）
- T4は未測定なので据え置き
- `_normalize_rows` は `rank_score` で並べ直すようにした。T0/T1/T2では従来の `sorted_index` 順を再現する
- テスト `tests/test_trainer_t3_rank_field.py`（6件、うち1件は実エンジンで精度3段階の勝者不変を要求）

保存ハンド6判断での前後比較: モデルと教師の不一致 **4/6 → 1/6**。

### 小さい減点は探索で裏取りしてから表示する（2026-08-15）

モデルは1回のforward passなので、**同点を同点と言えない**（異なる入力は異なる実数に写る）。
実測（`docs/t3_tie_misses_20260815.md`、166 root）では、探索が同点と判定するペアに
モデルが減点を付ける割合が**先攻5.2% / 後攻21.3%**。その主張額は最大0.118/0.272だった。

そこで **T3で、モデル採点のEVロスが 0 < loss < 0.30 のときだけ、その1決定を教師探索（`deep`）で
再採点し、探索の値を表示する**（`handlog.CONFIRM_STREETS` / `CONFIRM_BELOW` / `CONFIRM_PRECISION`）。

- 発火率はT3判断の41〜46%、1回あたり約2秒
- T0は1決定が分単位なので対象外。T1/T2は発生率が未測定なので保留（測ったら追加する）
- T4は厳密列挙なので確認するものが無い
- 判断行に `model_ev_loss` / `confirmed_by` / `overturned` が付き、UIは「探索で確認: 差なし」
  というバッジを出す（モデルが何と言ったかはツールチップに残す）
- **逆方向にも効く**: 実測でモデルが −0.044 と評価した判断を探索が −0.525 に訂正した例がある
- テスト `tests/test_trainer_confirm_small_losses.py`（7件）

### ターンを指定して1スポットだけ採点する（2026-08-15）

ハンド入力画面の「ターン」チェックボックス（未選択＝全ターン）。API では
`POST /api/handlog/analyze` の `turns: [2]`。**気になった1手だけに高い精度を払う**ための
機能で、上の表がそのまま理由になっている。実測（教師探索・同一ハンド）:

| 実行 | 判断数 | 所要 |
|------|-------|------|
| ハンド全体・`deep` | 5 | 88.7秒 |
| **T2のみ**・`deep` | 1 | **10.1秒** |
| T0のみ・`deep_t0` | 1 | 413.4秒 |

3行目のとおり `deep_t0` の時間はほぼ全部がT0なので、T2を最高精度で見たいだけなら
7分待つ必要がなくなる。

仕様上の要点:
- **絞るのは採点だけで、リプレイは絞らない**。指定ターンが直面した盤面・死札は
  全街を順に再生して作る。実測でハンド全体と指定ターンの採点はビット一致
  （rank 20、EVロス 1.3085367679595947）
- **保存はマージ**（`handlog.merge_analysis`）。部分結果でハンド全体の解析を
  上書きすると、一覧の `total_ev_loss` が1手分の損失をハンドの損失として表示してしまう。
  該当スロットだけ差し替えて合計を再計算し、各判断行に採点した精度を刻む
  （混在時は `mixed_precision: true`）
- FL席の一括配置はターン番号を持たないので、ターンを指定した実行では対象外
- `method=model` は1回のforward passで精度を読まないため、ターン指定の効果は小さい
  （1ハンド1〜2秒のまま）

**全ストリート・両席が m3 エンジン経路**（2026-08-07、m7v5 パッケージのピン14個を投入）。
MC は fallback としてのみ残る。実測（precision=fast、全候補ランキング）:

| ストリート | 評価器 | 候補数 | 先行 | 後攻 |
|-----------|--------|-------|------|------|
| T0 | `rust:t0` | 232 | 20.5秒 | 5.0秒 |
| T1 | `rust:t1` | 24〜27 | 0.45秒 | 0.26秒 |
| T2 | `rust:t2` | 9〜24 | 0.12秒 | 0.09秒 |
| T3 | `rust:t3` | 9〜21 | 0.03秒 | 0.02秒 |
| T4 | `rust:t4_exact` | 3〜6 | 即時 | 即時 |

- エンジン: `target/release/ofc_hu_m3_engine.dll`（**`.windows-target` の古いDLLはT1/T2非対応なので使わない**）
- 学習済み重み: `rust/hu_m3_engine/tests/fixtures/*.bin`（m7v5パッケージと同一SHA）

**ピンの依存関係**（エンジンは下流が揃わない街を拒否する）:

- T1先行 → `learned_t1_second` が必須（全ロールアウトが相手のT1後攻応手で始まる）
- T0後攻 → 下流7個、T0先行 → さらに `learned_t0_second` を足して8個
- これが「T0とT1先行がMCに落ちていた」理由。評価器の未実装ではなく**ピン不足**だった

**`fast_*`（蒸留版）を5個入れている理由**: 速度のためで、強さのためではない。
入れないとT0先行が**292秒**かかり、対話的に使えない（実測）。入れると20.5秒＝14倍速。
エンジンはこれらを使う評価器を `learned_fast` と報告する。T3/T4に蒸留版は存在せず常に全精度。

**FL定数の世代差**: T4(v6)/T3(v3,v2) は 9.6 でリラベル済み、T2以下は旧定数(10.227)のまま。
M7 cascade が T2 で進行中のため。DLL自体は 9.6 でビルド済み（ゴールデンピン24件で検証）。

**MC fallback のCRN修正（2026-08-12）**: 3人版M1の敵対的レビューで発見された欠陥の修正。
futures のカードは事前抽選していたが、ヒーロー配置と相手の slot シャッフルが候補ループ内で
共有 rng を消費しており、候補のEVが「その前にどの候補を評価したか」に依存していた。
修正後は候補非依存の乱数（継続カード・keep選択・相手の完成盤面）を future ごとに全部事前抽選し、
候補依存の行配置だけを future 毎シードの固定幅ストリームで読む（`ofc_regular.three_max.mc` と同一方式）。
**採点値が変わるため、エンジンが拒否した街の MC ランキング表示は修正前・凍結リリース
（ofc-regular-release-20260811）当時と一致しない**。副次変更: 死札過多で山札が継続を賄えない場合は
黙って切り詰めず ValueError、相手終端の事前計算で候補数分の再計算が消えて高速化。
ピンは `tests/test_trainer_mc_evaluator.py`（修正前コードでは order-independence テストが失敗することを確認済み）。

## 「モデルを使う」と「教師で採点する」は別物

これを混同すると桁で見誤る。同じT0先行の局面で:

| 操作 | エンジンのkind | 時間 | 何をしているか |
|------|---------------|------|---------------|
| モデルが打つ | `decide` | **0.09秒** | ルート扇へのforward pass。`evaluator: learned` |
| 教師が採点する | `t0` | **19.9秒** | 下の全ストリートを探索。このモデルのラベルを作った当のもの |

220倍差。トレーナーは**両方**要る — 採点には全候補のEVランキングが要るので教師、
AI対戦相手は1手あればいいので `decide`。

**AI対戦相手は `decide` を使う**（`game.py::_opponent_move`）。ここをランキングにしていた頃は、
後攻で1ハンド始めるたびに**19.5秒**、誰も読まないランキングをAIのために回して待たされていた。
`decide` にして0.2秒。エンジンが拒否した場合はランキング経路にフォールバックするので、
ピンが揃っていない環境でも対戦相手は動く。

## 実測レイテンシ（precision=fast、1ハンドの立ち上がり）

| | 先行 | 後攻 |
|---|------|------|
| 配札→自分が打てるまで | 0.1秒 | 0.2秒 |
| AIの応手 | 0.7秒 | 0.2秒 |
| 自分のT0の採点が出るまで | 18.5秒 | 6.3秒 |

**T0の採点だけは重い**。232ルート×最深の木という形に由来する固有コストで、設定ミスではない。
枝刈り機構（`prefilter_samples` / `race_schedule`）はどちらも**粒子数**を削るもので、
こちらは既に最小の1粒子なので効かない。

採点はカードが配られた瞬間からバックグラウンドで走る。5枚を置く操作をしている間に
進むので実用上はかなり隠れるが、**即座に確定すると待たされる**。T1以降は全て1秒未満。

## AI対戦相手

エンジンの `decide` が返す手をそのままプレイ（＝学習済みモデルの手）。全ストリートがモデル経路になったため、
**本番webappより強い**（本番の `assembly.json` は T0/T1/T2先攻 を `python_policy` に流しており、
T0/T1の学習済みモデルを1つも使っていない）。本番AIの挙動を再現したい場合はここが乖離点。

## FL（ファンタジーランド）

v1ではFL突入を検知して固定EV（+9.6、`configs/fl_ev_regular_v4_selfplay.json`）を結果に表示するのみ。
定数は `trainer/fl_ev.py` がこのconfigから読むので、configが更新されれば自動で追従する。

**解消済み（2026-08-07）**: かつてDLLのビルド(08-05 23:49)が `infoset.rs` の 9.6 化(08-06 19:59)より
古く、エンジンだけ旧定数で動いていた。`cargo build --release -p ofc_hu_m3_engine` で再ビルド済み。
検証は `t0_pruning_safety` / `t0_stage_two_racing` の24件（`a_raced_run_is_deterministic_and_pinned`
含む）で、これらのゴールデンピンは 08-06 に 9.6 用へ再ピンされたもの。全件パス。
DLLのバイト列から定数を直接読む方法は使えない（インライン化されていて f64 リテラルとして現れない）
ため、挙動での検証がここでの唯一の手段。

なお fleet の Linux `.so`（`e17aa39f…`）とはバイト一致しない。プラットフォームが違うため当然で、
担保できるのは「同一ソース・同一定数からのビルドでゴールデンピンが一致」まで。
旧DLLは `target/release/ofc_hu_m3_engine.dll.pre96-backup` に退避してある。
FLハンド自体のプレイ・採点は未実装（`regular_fl_solver.exe --solve` で拡張可能）。
