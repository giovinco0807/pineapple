# ボトムアップ・ループ設計: T4→T0を複数周する (2026-07-29)

## 前提

`all_turn_ai_goal_and_milestones.md`の**完成条件9**は既にこれを要求している。

> T0/T1/T2方策を更新した後に、その行動尤度でT3/T4 rangeと方策を再解決し、
> 全ターン方策とpublic posteriorの固定点iterationが独立seed間のdrift閾値へ
> 収束する。**古い上流behaviorに条件付けたままのT3/T4を最終版として扱わない。**

したがって「T4→T0を数回まわす」は追加要件ではなく、M7として既に定義された
必須工程である。本書はその実行設計を具体化する。

## なぜ1周では終わらないか（ターンごとに理由が違う）

周回が必要な理由は2つあり、ターンによってどちらが効くかが異なる。

| 理由 | 内容 |
|---|---|
| **A: 入力分布のずれ** | 学習時のroot分布と、実際に強い方策同士が到達する局面の分布が違う |
| **B: 教師そのもののずれ** | ラベルが下流方策・相手モデルに依存するため、それらが変わると正解が変わる |

**T4先攻はAだけが効き、Bは効かない。** ラベルは「与えられた
(自盤面, 相手盤面, 既知デッドカード) に対する宣言belief下の厳密EV」であり、
**どの方策とも無関係に定まる**。相手のT4後攻応手も終端最大化なので方策依存が
ない。したがってT4先攻の周回は「on-policy分布で引き直して**厳密に**貼り直す」
だけでよく、教師の正しさは周回間で劣化しない。これは非常に有利な性質である。

**T3以上はAとB両方が効く。** T3のラベルは下流（T4）方策と相手のT3方策に依存し、
上流（T0〜T2）が変われば到達分布も相手のrangeも変わる。ここが本来の固定点反復。

## ループ設計

```
pass k:
  1. T4先攻: root分布を pass k-1 の方策から生成 → 厳密解で貼り直し → 再学習
  2. T3後攻 → T3先攻: 下段の評価器を葉にして解く → 学習
  3. T2 → T1 → T0: 同様に下から
  4. drift測定: pass k と pass k-1 の方策をターン別・席別・Joker層別に比較
  収束したら終了、しなければ pass k+1
```

### root分布の作り方（重要）

pass 2以降を**純on-policyにしてはいけない**。現方策が避ける局面の評価器が壊れ、
そこを突かれる。各passのroot集合は次の混合とする。

- **on-policy 70%**: pass k-1 の方策同士の自己対戦から到達した局面
- **一様ランダム 20%**: pass 1と同じ無フィルタ生成（カバレッジ下限の保証）
- **敵対的 10%**: 現方策の予測誤差が大きい局面、Joker 2枚などの希少層

この配分自体をpass間で固定し、変える場合はversionを上げる。

### 収束判定

pass k と k-1 の間で、以下をターン×席×Joker層(0/1/2)ごとに測る。

| 指標 | 閾値（初期案、実測後に確定） |
|---|---|
| 方策TV距離（同一rootでの行動分布の差） | 平均 < 0.02、最大 < 0.10 |
| Top-1一致率 | > 95% |
| 厳密解に対するregret（T4先攻のみ測定可能） | 平均 < 0.01点/手 |
| 独立seed間のdrift | 上記の変動が閾値の1/2以内 |

**T4先攻はregretを厳密に測れる**（厳密解が手元にある）ので、他ターンの
収束判定の較正基準として使う。他ターンは厳密解がないためTV距離が主になる。

## 想定周回数とコスト

過去の類似作業（regular側のt4_model v1→v5）から、**3周前後**を見込む。

| pass | T4先攻 | T3 | T2〜T0 | 備考 |
|---|---|---|---|---|
| 1 | 一様ランダム150k root、1.1時間 | — | — | 実行中 |
| 2 | on-policy混合で貼り直し | 初回solve | 初回 | 最も重い |
| 3 | 同上 | 再solve | 再構築 | 収束確認 |

T4先攻の周回コストは**1周あたり約1.1時間 + 学習数分**と安い（厳密解が
36〜38 roots/秒で回るため）。重いのはT3以上のsolveで、ここはGCPが要る。

## 打ち切り条件

- 3周して収束閾値を満たさない場合、周回を続けず**原因分析に切り替える**。
  収束しないのは設計の問題（特徴不足、belief不整合、root分布の偏り）であり、
  周回数を増やして解決する種類の問題ではない。
- 各passの成果物はversion付きで保持し、前passを削除しない。
- pass間で評価器を差し替えたら、その評価器を葉に使う上流artifactをstale扱い
  にする（既存の運用ルールと同じ）。
