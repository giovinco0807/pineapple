# 速い審判 — 継続手を蒸留してロールアウトを2.65倍に (2026-09-02)

対通常(ジョーカーHU)の審判は1ロールアウト130msで、レギュラー版が使う粒子数
(共通乱数256p×最大8バッチ)を払うと**T0-BTN 5局面で33時間**。その値段の
出どころを実測し、蒸留で潰した記録。**検収合格・採用**、配信は不変。

## 1. 値段の解剖 (実測)

街別の1ロールアウト単価(その街から終局まで、両席込み):

| 開始街 | ms/rollout | 限界コスト |
|---|---|---|
| T0 | 129.9 | +72.7 |
| T1 | 57.2 | +24.0 |
| T2 | 33.2 | +30.8 |
| T3 | **2.5** | — |

T3以降が桁違いに安いのは厳密解だから。`--serve-joint-samples` を200→50に
落とすと198→99msになるので、**半分以上がjointブロックのサンプリング**。

トレースの `by` フィールドで決定者を数えると、モデルが判断しているのは
**5スロットだけ**: t1_bb / t1_btn / t2_bb / t2_btn / t3_bb。
t3_btn は closed-form、t4 は exact-v4、t0_bb は policy.bin(54次元)。
つまり130msの正体は**この5決定 × 各20候補前後 × joint符号化2個**。

## 2. 蒸留 — 方策型は失敗、評価器型が勝った

同一教材・同一ラベル(チャンピオンが選んだ**手**。値ではない)で2形式を比較:

| スロット | 方策型 (state→27ロジット) | **評価器型 (候補盤面→スコア)** |
|---|---|---|
| t1_bb | 31.6% | **68.7%** (top3 94.6%) |
| t1_btn | 24.5% | **63.6%** (90.3%) |
| t2_bb | 24.4% | **61.1%** (88.4%) |
| t2_btn | 22.3% | **57.9%** (85.8%) |
| t3_bb | 18.8% | **52.3%** (80.7%) |

方策型は「27通りの結果盤面を想像する」ことを要求するが、チャンピオンは
そんなことをしない — 候補盤面を符号化して点を付ける。**評価器型は同じ
仕事の形**で、ラベル効率も27倍(1決定から27候補の比較信号)。約2倍の差。
データ3.9万→21.4万でさらに+8pt。

**教材**: チャンピオン自己対戦21.4万ハンド(艦隊16台、~$8)。1ハンドから
7決定。`ai/tutor/hu_fast_material.py` → `train_hu_fast_eval.py`。
入力487次元は全部その場で数えられるもの(盤面one-hot、見えた札、段別統計)。
**試写ゼロ**。

## 3. 検収 — 3段階

**① パリティ**: 訓練済み重みで Rust↔Python、1,062候補ベクトルで
**特徴量の差 0.000e+00**、スコア差1.07e-05(f32累算順序)、**argmax 40/40一致**。

**② 順位の保存(浅い)**: 96ロールアウトで fast ρ=0.513 / 対照(チャンピオン
同士・別シード) ρ=0.510。**差が出ない** — が、これは合格ではなく
**この深さでは何も言えない**という意味。1候補のSEが約2点で、候補同士が
その中に収まっている。hand 0 は fast が6位を選んで5.46点落としたが、
**対照も4位を選んで4.14点落とした**。

**③ 順位の保存(深い、512ロールアウト)**:

| hand | fast ρ | 最善手 | 損失 | 対照 ρ | 最善手 | 損失 |
|---|---|---|---|---|---|---|
| 0 | +0.979 | ✓ | 0 | +0.923 | ✓ | 0 |
| 1 | +0.252 | ✓ | 0 | +0.483 | ✓ | 0 |
| 2 | +0.706 | ✓ | 0 | +0.643 | ✓ | 0 |
| 3 | +0.734 | ✓ | 0 | +0.797 | ✓ | 0 |
| 4 | +0.741 | ✓ | 0 | +0.923 | ✗ | +0.38 |
| 平均 | +0.683 | **5/5** | **0.000** | +0.754 | 4/5 | +0.077 |

**採掘が読む指標(最善手一致・価値の損失)では fast が対照を上回った。**
hand 4 では fast が当てて対照が外している。ρは対照がやや高いが中位以下の
話で、hand 1 のように512でもチャンピオンが自分を0.48しか再現できない
局面に引きずられる。

**速度 2.65倍** (75→28 ms/rollout、T0-BTN設定)。エージェント計測の1.77倍
より良いのは、T0-BTN審判では相手のT0が固定され232手の決定が消えるため。

## 4. 使い方と境界

- `--hu-fast-nets <dir>` — 5枚(t1_bb t1_btn t2_bb t2_btn t3_bb)を要求。
  1枚でも欠けたら**ハードエラー**(半分だけ速い審判は解釈不能な第3のゲーム)。
- **審判モードのみ** (`--hu-t0-deep` / `--hu-deep-replay`)。配信は不変で、
  fastを渡した `--hu-mirror` がバイト同一であることを検証済み。
- 値は**チャンピオン継続の値と比較不可**(継続が弱いので全候補が下がる)。
  読んでよいのは順位だけ。

## 5. 既知の欠陥・次

1. **特徴量8番目の取りこぼし**: Pythonが `flush_outs` を計算しながら
   返さず、代わりにペア化アウツを返している(`train_hu_fast_eval.py`
   `row_stats`)。Rustはコードに合わせてあるのでパリティは保たれるが、
   フラッシュのアウツは対FL戦役で有効性が実証済みの特徴。**v2で足す**
   (幅が488になるので両側同時変更＋パリティ再取得)。
2. t0_btn は未蒸留(行動空間が232手で別形式)。T0-BTN審判では相手T0が
   固定されるため現状は不要。
3. ρが局面で0.25〜0.98と大きく振れる。「解像に必要な深さ」は局面ごとに
   違うので、採掘は**固定深度でなく淘汰レース**で組むべき。

## 追記 (2026-09-02 午後): deep_replay の2つのジョーカー欠陥と、この文書の数字が無傷である理由

失点地図の器具を `--hu-deep-replay` の上に作ろうとして、同経路の欠陥を2つ踏んだ。
**本文の数字はすべて `--hu-t0-deep` (`t0_deep_eval`) 経路で取ったもので、
その経路は別実装で正しく、影響を受けない**(エージェントがコードで確認)。

1. **強制履歴のジョーカー綴り**: トレース由来の履歴が `X1` と綴られていても、
   再配札で相手の未来の引きにジョーカーが入ると同じ札が `X2` に renumber され、
   正しい履歴が「この配牌のものではない」と拒否される。86.8%のハンドに
   ジョーカーがあるので測定の過半が落ちた。修正: 強制札を「その席の17枚の
   何番目か」で保持し、ロールアウトごとに綴り直す(`t0_deep_eval` と同じ手法)。
2. **再配札のジョーカーが決定的**: `replay_deal` がシャッフルからジョーカーを
   除去し、固定位置(3番目と10番目)に再挿入していた。修正前バイナリで200
   ロールアウト回すと到着先は `{[(1,1),(2,1)]}` の**1通りだけ**。しかも
   どの席・街に来るかが replay 対象で決まり、(0,0)なら両方相手、(0,1)なら
   両方ヒーロー — マス間で比較不能。修正: シャッフルの位置のまま、未出の
   枚数分だけ名前を付けて採用する。既出2枚の履歴144件・再配札なし48件は
   バイト同一、変わったのは「未出のジョーカーを置く」ケースだけ。

**無効になった数字**: `--hu-deep-replay` でジョーカーが未出だった局面の結果
(今日の費用計測のみ。時間の測定なので実害なし)。
**無傷**: 本文の全数字、T0-BTN 5局面、T0-BB採掘(いずれも `t0_deep_eval`)。

発見の経緯: 器具を走らせる前に5観点×反証の監査ワークフローをかけ、
統計の欠陥4件(4バッチの `3*se` は自由度3のt検定で帰無下2.9%が確定、
レギュラー版8/22訂正と数値同型)と一緒に出てきた。50時間の測定を燃やす
前に止められた。
