# T0-BB の相手ブロックは 97% の計算で 0 の情報を運んでいる (2026-08-24)

オーナーの指摘「T0-BB で毎回相手をサンプリングするのはアホ」「相手が何を引くとか
関係ない」から始めた調査。**指摘は正しく、しかもレギュラー側では既に実装済みの
設計判断だった。** ジョーカー側だけが払い続けている。

---

## 1. 事実

### 1.1 T0-BB の入力は、配られた5枚しかない

on-policy リクエスト 2,000 行を調べた結果:

| 入力 | 相異なる値 |
|---|---|
| 自分の盤面 | **1種類** `[[], [], []]` |
| 捨て札 | **1種類** `[]` |
| 相手の盤面 | **1種類** `[[], [], []]` |

盤面・捨て札・相手はすべて常に空。**変わるのは draw の5枚だけ。**

### 1.2 相手ブロックは候補間で定数

`hu_match.rs:509-524` は `opponent_tail` を候補ループの外に出しており、コメントが
理由を書いている: 「相手側は全候補で同じ」。**定数は 232 候補の順位付けに寄与
できない。**

### 1.3 その定数が計算量のほぼ全部

`joint_outlook.rs` の `arrangements()` は **上限で打ち切る前に全列挙する**
(`recurse` が全通り作り `prune` が 32 本に間引く)。したがって1サンプルあたり:

| | 空き枠 | 列挙数 | 配信での回数 | 合計 |
|---|---|---|---|---|
| **相手ブロック** | **13** | **13!/(3!5!5!) = 72,072** | 1 | **72,072** |
| ヒーロー候補 | 8 | ≤ 8!/(3!3!2!) = 560 | 4 (topk) | ≤ 2,240 |

**相手ブロックが列挙作業の約 97%。**

### 1.4 実測: 1決定の時間は丸ごとサンプリング

候補4本(= 配信と同じ形)、`--hu-t0-deep --rollouts 0`、KKの手 (Ks Kd 6d 5h 3h):

| joint samples | 実測 | 1サンプルあたり |
|---|---|---|
| 200 (出荷) | **45 s** | 0.225 |
| 100 | 21 s | 0.210 |
| 12 | 2 s | 0.167 |

**切片がほぼゼロ。** ネット推論も構造的特徴の組み立ても、測れる大きさではない。
T0-BB の 1 決定は、実質すべてが joint サンプリングである。

按分すると **45 秒のうち約 44 秒が相手ブロック**。ラベル生成で T0-BB が 15.7 s/root、
T0-BTN が 3.5 s/root と 4.4 倍だった理由もこれで説明がつく。

### 1.5 サンプリングは入力の 7.7% しか作らない

エンコーダのブロック構成 (`encode_hu_teacher.py:228-229`):

```
own: actor48 + rowwise41 + joint8 + context7 + alloc6 = 110
opp: actor48 + rowwise41 + joint8                     =  97   合計 207
```

**joint8 × 2 = 16 次元 / 207 次元 = 7.7%。** 残り 191 次元は決定的に作られる。
「サンプリングありきのモデル」ではない。

## 2. レギュラー側は同じ問題を認識し、ゼロで埋めている

`regular-ofc-pineapple/rust/hu_m3_engine/src/fast_features.rs:119-137` に専用の
エンコーダ `fast_encode_hidden_opponent` があり、docstring がそのまま言っている:

> 相手の盤面が読めない場合の 1 候補 168 特徴: 構造的特徴、粗いヒーロー見通し、
> **そして相手が入るはずの場所にはゼロ**。(中略) **1つ目は、先手で打つ開幕
> ストリート。相手はまだ動いておらず、盤面は空 — 13 枠** (中略)
> どちらの場合も、**相手を読む 2 つのブロックはゼロのまま置かれる**。

さらに `fast_outlook_block_only` があり、「head-to-head 列がゼロのままなので、
ここで作った finishes は読まれずに捨てられる」と明記して**読まれないものを作らない**
最適化まで入っている (`docs/cpu_quickwins_20260820.md` の3つの高速化の1つ目)。

| | レギュラー | ジョーカー |
|---|---|---|
| T0先手の相手ブロック | **ゼロ**(計算しない) | **13枠 × 200サンプル** |
| 専用エンコーダ | `fast_encode_hidden_opponent` | 無し(全街同じ経路) |

レギュラー側はこれを近似ではなく**構造的に正しい**と扱っている。相手が動いていない
以上、相手側の特徴に入れるべき情報は無い。

## 3. 途中で撤回した主張(記録)

1. **「サンプリング雑音がランキングを揺らす」→ 誤り。** joint の抽選シードは
   局面 id 由来 (`node_seed = format!("replay-rank/{street}/{seat}")`) で、
   `--self-play-seed` とは無関係。3シードで走らせてスコアが小数以下まで完全一致
   した。**joint ブロックは局面ごとに決定的**で、実行ごとの雑音ではない。
2. **「上位は極めて安定」→ 1局面での誤り。** KK 1局面ではサンプル数 200→12 でも
   1位が動かなかったが、**12局面**に広げると:

   | samples | 1位一致 | top-4共通 | 順位ズレ |
   |---|---|---|---|
   | 50 | **9/12** | 3.00/4 | 8.1 |
   | 12 | **5/12** | 2.50/4 | 15.0 |

   [[leaf-truncation-costs]]「1ルートのスモークは順位統計にならない」の再演。
   1位-2位差が小さい局面ほど動く(gap 0.079 の局面は 50 で既に変化、
   gap 3.102 の局面は 12 でも保持)。
3. **「相手ブロックは無作為に組む」→ 不正確。** `sampled_joint_block_shared` は
   32 通りの並べ方を試して**最良を取る**。採点式は `royalty + fl_ev`(ファウルは −6)で、
   **対戦相手との比較は入っていない**。相手の盤面が単体でどれだけ立派になるかの
   8 統計(ファウル率・平均・生存royalty・生存FL・sd・6点以上率・15点以上率・生存平均)。

## 4. 実施済み — 速度は5倍、強さは動かず

**変更**: `joint_outlook::sampled_joint_block_shared` の先頭に、まだ誰も打っていない
盤面(空き枠 = [3,5,5])なら8ゼロを返すゲートを置いた。**配信と訓練の両経路が必ず
通る最内側**なので、両者が規則を違えて述べることが構造的に起きない
(配信 `hu_match` → `opponent_tail` → `board_blocks` → `_shared`、
訓練 `encode_hu_teacher.py` → `--joint-outlook` → `solve` → `_shared`)。

FL14 経路は全呼び出し元を調査済み: いずれも「候補が到達した盤面」を符号化しており
開始局面そのものは符号化しないため、空盤面は届かない。境界は
`one_placed_card_is_still_computed` テストで固定。

**明示フラグにしなかった理由**: `encode_hu_teacher.py:130` は block リクエストを
`(board, pool)` で重複排除しており、**自分/相手のロールはリクエストが書かれる前に
落ちている**。ロール依存の規則はこの重複排除自体を壊す。`(board, pool)` の純関数
である規則だけが訓練と配信の一致を保証する。

### 結果

| 項目 | 実測 |
|---|---|
| 1決定 (232候補) | **21 s → 3 s** |
| **再エンコード (13,103ルート・20シャード)** | **3時間 → 36分(5倍)**、約$2 |
| 特徴量の変化 | 244万行で **199-206 のみゼロ化、他199次元は完全一致** |
| T0-BB regret (dev) | 0.99897 → **0.71397**(MAE 3.7445 → 3.5759) |
| **ミラー判定 12,000ディール・2セット** | **−0.038 [−0.166, +0.092] 差なし** |

判定の内訳: nj1 −0.025 / nj1b −0.052(両セット同符号で除去版がわずかに上、
どちらもゼロを跨ぐ)。FL価値ゼロ採点でも +0.013 [−0.038, +0.065] で差なし。
foul 26.0/26.3%、FL入場 32.5/32.6%、**一致率81%** — 打ち筋はほぼ同じ。

### 読み

**候補間で定数の8次元を消しても対戦は動かない。** 相手ブロックが判断に寄与して
いなかったという読みと整合する。得られたのは**速度のみ**で、ラベル生成が5分の1に
なる。

**regret −29% は対戦に転写しなかった** — 忠実度と勝敗の断絶、6例目。ただし今回は
悪化でもない(過去5例は「改善が転写しない」、今回は「改善が転写しないが害もない」)。

**「差なし」を「無害」の証明として読みすぎないこと。** 1スロットの差は8スロット
全入れ替え(lap2 全体 +0.325)の一部にすぎず、12,000ディールの分解能は ±0.13。
真の差が 0.1 級なら検出できない。言えるのは「大きな害はない」まで。

### 出荷の判断材料

強さが同じで5倍速いので、**次のラップからこの符号化を使う**のが費用面では明らかに
正しい。ただし出荷は世代境界の判断であり、以下が伴う:

- 既存の T0-BB コーパスは旧符号化製(`t0_bb_enc_lap2`)。新は `t0_bb_enc_nojoint`
- モデルは `D:/ofc_data/hu/t0_bb_nojoint_s20260815`、bin は
  `D:/ofc_data/hu/t0_bb_nojoint.bin`(sha `95ccc4d9...`)
- バイナリは binstamp **20260824a**(sha `407ca9ce...`)、ソースは
  `hu_src_20260824a.tar.gz`。**古いバイナリと新コーパスを混ぜない**こと

### 運用メモ

**ビルドVMは自滅に失敗する。** `build_t1_binary.sh` は最後に自分を消すが、
サービスアカウントに `compute.instances.delete` 権限がなく
`Required 'compute.instances.delete' permission` で落ちる。ビルド自体は成功する
ので**手動回収が要る**(max-run-duration が最後の砦)。

**再エンコード用のソース tar を組むときは fl_ev に注意。** 旧 tar は 5.28、
リポジトリ現行は 6.57。**再エンコードするラベルは 5.28 の下で作られている**ので、
現行を入れると特徴量が「相手ブロック除去」と「fl_ev 変更」の2つの理由で変わり、
対戦結果の原因が分離できなくなる。同じ理由で `main.rs` も旧 tar 版を保つ
(リポジトリ版は `fl_sim` を参照するが tar に `fl_sim.rs` が無くビルドが落ちる)。

## 5. 参考: 当初案(実施前に書いたもの)

**変更**: T0-BB(および対FL)で `opponent_tail` の計算を飛ばし、相手側 97 次元を
ゼロで埋める。レギュラー側と同じ扱い。

**期待効果(按分からの外挿、実測ではない)**: T0-BB の 1 決定 45 秒 → 1〜2 秒。
ラベル生成の T0-BB 15.7 s/root も同オーダーで下がる。

**必須の前提**:
- **ラベルを作り直す。** 入力が変われば訓練時の分布と食い違う。今日のランカー
  実験([[t0-ranker-ablation]])は、まさに「配信側だけ変えて弱くなった」例。
- **対戦で測るまで出荷しない。** 速くなることと強くなることは別で、
  このプロジェクトは忠実度→対戦の断絶を5回踏んでいる。
- 世代境界の作業になる(fl_ev の凍結、コーパスタグの分離)。

**測っていないこと**: 相手ブロックを実際に外して速度と強さを測ってはいない。
上の 97% は列挙数による按分であって、直接測定ではない。

## 6. 波及: T0-BB は本来もっと小さい問題

T0-BB の状態は 5 枚のみ(§1.1)。レギュラー側はこれを数え上げていて、
**T0先手は 134,459 の正準局面**(2,598,960 をスート同型で畳んだ数、Burnside)。
スート対称が使えるのは**この街だけ** — 先手が置いた瞬間に消える。

レギュラー側には既に逐次消去の実装と参照表があり
(`hu_t0_sequential_elimination_v1.py` / `hu_t0_elimination_runner_v1.py` /
`hu_t0_solved_openings_v1.py`)、24局面中19局面が解決済み、`trainer/engine_eval.py`
に**表から 0.2 ms で答える**未コミット変更が入っている。

そこで見つかった壁も記録されている(`docs/t0_handoff_20260821.md`):

- **1,024粒子 1バッチでは順位が付かない**(トップ2差の散らばり SD 0.475、
  真の差が 0.9 超でないと分離できない)。24局面中9局面しか越えず、
  そこから出した「平均regret 0.107」は**真値の約4倍**
- **モデルの値は使えないが篩としては優秀** — 相関 0.841 / MAE 4.11 で順序が逆転する
  局面がある一方、17局面すべてで実測最善を 232 中 3 位以内に入れた。
  **今日のランカー実験と同じ構図**
- 全 134,459 を消去法で解くと **約 $31,000**(GCP Spot 見積り)

レギュラー側の未解決の第一問は「**モデルは実際いくつの局面を必要とするのか**」で、
約 $700 の学習曲線で「1万か10万か」が分かるとされている。**それが1万なら表は不要**
になるので、ジョーカー側で同じ道を始める前にその答えを待つのが順当。

ジョーカー側固有の差: **ジョーカー2枚でスート対称が壊れる**(ジョーカーはスート置換で
不変)ので正準局面数は 134,459 より増える。数え直しが要る。
