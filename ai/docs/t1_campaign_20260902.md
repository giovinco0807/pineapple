# T1戦役 — 質は効き、雑音のままの量は効かない (2026-09-02)

T2戦役([t2_width128_20260831.md](t2_width128_20260831.md))の道具一式を
1街手前へ転用した記録。**結論: fit研ぎ版が審判ゲート +0.0287/root で合格
(未出荷)。90k量産は雑音ラベルで作ったため逆効果だった。**

## 0. 前提 — T1ラベルの意味論(調査で判明した訂正)

- 現行 `lap4_t1_own` は `own_only:true, t4_draw_sample:0`、`truncate_depth`なし
  = **フル降下+厳密own-worth終端**。`encode_fl14_t1.py` の docstring と
  `encoded_96/manifest.json` の "truncate_depth 0" 記述は lap2/lap3 時代の
  stale テキスト。
- サンプルされる量は **T2引き(既定24) × T3引き(既定12)** のみ。ノブはCLIでなく
  リクエストJSONのフィールド(`t1_vs_fl.rs:57-79`)。
- ルートは played (deals→`--play-roots --play-t1-output`)、id = 3238498113+序数。
- 配信 `own_lap4/t1.bin` = `model_s20260815/evaluator.bin`、**96次元**
  (cheap-drawもjointも持たない唯一の街)、~1.7ms/候補。

## 1. 測定器 — T1版sharpdev (艦隊6台, ~$4, 35分)

dev 498ルートを **t2_samples 24→96、2独立パス**(id接頭辞 p1//p2/ でストリーム分離)。
ローカル6時間の見積りをVM化で1時間弱に圧縮。

| 指標 | 値 |
|---|---|
| 旧ラベルの argmax が研ぎで覆る率 | **126/498 = 25.3%** (T2は30.2%) |
| 旧best手を教える損 | 0.489点/該当ルート、全dev平均 0.124 |
| 真の同点圏(top2 < 2SE) | 220/498 = 44.2% |
| **出荷T1の真のregret** | 公称 0.506 → **0.329** |

## 2. 質の実験 (fit研ぎ、艦隊6台 ~$6)

fit 3,990ルートを96drawsで再ラベル → **特徴・アーキ不変、yだけ差し替え**。
dev は両アームとも研ぎ済み(選択条件を揃え、T2で確認した選択バイアスを排除)。

| アーム | 3シード | 平均 |
|---|---|---|
| ctrl (旧24draw fit) | 0.356 / 0.319 / 0.355 | 0.343 |
| **fit96** | 0.321 / 0.295 / 0.326 | **0.314** |

3シード全ペアで改善、**−0.03 (−8.5%)**。T2の−20%より穏やかで、誤正解率の差
(25.3% vs 30.2%)と整合。

## 3. 量の実験 — 失敗 (艦隊10台+補充, ~$35)

`--emit-t1-roots`(新規実装、5,480 roots/分)で正典チェーン
(models_ship_20260902)から90,000ルートを実プレイ生成 → 艦隊でラベル。
分布は原本と同族(mean 5.08 vs 4.76、std/分位点一致)。

| 構成 | 3シード | 平均 |
|---|---|---|
| fit96 (研ぎ4k) | 0.321/0.295/0.326 | 0.314 |
| **100k (研ぎ4k + 新90k)** | 0.333/0.335/0.316 | **0.328 ← 悪化** |

**原因は設定ミス**: 90kを **t2_samples=24**(原本と同じ雑音設定)で量産し、
clean 4k を noisy 90k で薄めた。T2の量産は96draws相当だったのが決定的な差。
90kルート資産自体は無傷 — 96drawsで再ラベルすれば量の効果を取りに行ける
(~$140、艦隊5-6時間)。

## 4. 検収 — 審判ゲート

dev 498ルートでは **全候補が未決着**(CI半幅0.04-0.07 > 差0.03)。
T2の1,022ルート+低雑音ラベル(SE 0.005)に対しT1のdevは解像度が足りない。
→ 判定は新規3,000ルートの審判ゲートへ委任。

- ルート: `--emit-t1-roots`、未使用シード帯 8238398113
- 候補列挙: t2_samples=1 の安価パス → 疑似ラベル → 96次元エンコード
- 両腕とも**配信binイメージ**で採点 → 不一致 331/3,000 (11%)
- 審判: 不一致ルートのみ96draws×2独立パス(T1ラベラに`--keep-file`が無いため
  全候補価格付け)

**結果: 挑戦者(fit96_s15) − 出荷中 = +0.02873/root
[+0.01103, +0.04728]、ラベル雑音SE 0.00183、117勝101敗。CHALLENGER BETTER。**

注記: 331不一致のうち **222で評価**(艦隊2シャードがログすら残さず失敗、
ローカル再計算はセッション終了で中断)。未評価109は差0として計上。
CIは決着済みだが、完全版は残り109の審判で更新されうる。

## 5. 運用の教訓 (この日の授業料)

1. **`--skip-done` はVMの生存で判定するため、完走して自己削除した窓も
   再作成する**(空回り)。窓のチャンク完了数で判定すべき。
2. **完了済み窓のVMが空回りすると実効並列度が落ちる** — 終盤で1チャンク/15分
   まで低下。対策: 欠けだけを詰め直した独立runを立てる(t1gap方式、8台45分)。
3. **ログを残さず失敗するVMがある**(t1gate shard 222/555が2回とも)。
   既知の「到達性の穴」と同型。ゾーンを変えても再発したので原因未特定 —
   ログ空 + 出力空 なら諦めてローカル/別runへ回すのが早い。
   **かつ、そういうVMは生き続けて課金する**(撤収時に発見)。
4. **bash形式パス(/c/...)をネイティブexeの--outputに渡すと空ファイルになる**。
   Windowsパスで渡すこと。
5. `gcloud storage ls | wc -l` の値が実オブジェクト数と食い違うことがある
   (30 vs 実20)。完了判定はオブジェクト名の照合で行う。
