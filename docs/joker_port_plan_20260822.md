## 0. 結論

**移植は可能。ただし初版が言ったほど「既存部品でほぼ済む」わけではない。**
ジョーカー側は「1本のRustバイナリ + 平坦なフラグ群」で、レギュラーのような
サブコマンドやC ABIの関数分岐は無い。役割は揃っているが、呼び出し方が違う。

| 段 | ジョーカー側の実体 | 移植の重さ |
|---|---|---|
| A. on-policy局面の収集 | `--hu-trace` がトレースを吐き、`ai/tutor/extract_onpolicy_requests.py` が街×席のリクエストに割る | **既存** |
| B. 扇の値付け | 2系統ある(下記1)。ロールアウト系は候補限定も可能 | **既存** |
| C. 判定 | 無し。統計だけ書く。**ただし4σではなくジョーカー側の流儀に合わせる**(下記) | 小 |
| D. 再学習 | `train_t4_first_evaluator.py` はあるが **warm start も per-sample 重みも無い** | **中**(下記5) |
| E. ミラー対戦ゲート | `--hu-mirror` + `launch_verdict.sh`。**対差分の集計スクリプトはリポジトリ外** | 小〜中 |

## 1. インターフェイスの実体(検証済み)

エンジンは `ai/rust_solver/t4_first_exact/`(`src/hu_match.rs` 1,530行が本体)。
`fl_solver` ではない。モードは `Cli` 構造体のフラグで切り替える。

| 用途 | ジョーカー側の実体 |
|---|---|
| モデルに一手を選ばせる | 独立した呼び出しは無い。方策ループは `hu_match::play_hand` に内蔵。外から届くのは `--hu-deep-replay --rollouts 0`(全候補をモデルスコア順に出す)と `--hu-t0-deep --rollouts 0` |
| teacher(値ネット・葉打ち切り) | `ai/tutor/hu_street_teacher.py`(Python)。`--seat` と `--value-model` で街と席を選ぶ |
| teacher(ロールアウト・終局まで) | `hu_match::deep_replay`、`hu_match::t0_deep_eval`。CLI は `--hu-deep-replay` / `--hu-t0-deep --rollouts N` |
| 候補の限定 | `--t0-keys-inline` / `--t0-keys`(ロールアウト系のみ)。値ネット系には無い |
| on-policy トレース | `--hu-trace <hands> --trace-chunk` → `hu_match::trace_range` |
| 街×席への切り出し | `ai/tutor/extract_onpolicy_requests.py` |
| ミラー対戦 | `--hu-mirror` → `hu_match::mirror_hands`。1ディールを席交換で2回、id共有 |
| ピン | **テーブルは無い。コマンドラインの `--hu-a-models`(8スロット)/ `--hu-a-rankers`(8)/ `--arm-a-own`(3)** |
| 重み形式 | 平坦な `.bin`(マジック `T4F1`)。`.npz` は値ネット、`.pt` は訓練チェックポイント |

**共通乱数はロールアウト系にある**: 1ロールアウトにつき1つの未来を全候補へ
配り直す実装で、候補間の差が対になる。地図の測定にはこちらを使う。

## 2. マスは 7

T3-BTN は厳密解(swapped V4)、T4 は両席とも厳密/閉形式。
**ただし `--hu-a-models` には8個すべてのパスを渡す必要がある**(片方でも `none`
にするとその街が丸ごと無効化され、自分の手だけを見る選択器に落ちる。これは
実際に踏まれたバグで、+0.286 の差として記録されている)。

## 3. ジョーカー特有の注意

1. **扇は増えない。** ジョーカーは普通の1枚として置かれ、rank/suit は採点時に
   最良補完で決まる。T0=232、T1〜T3≤27(行が埋まると減り、実例で12)。
   **行動空間の移植作業は不要。**
2. **ジョーカーの名前は席ごと。** 各席が自分の1枚目を `X1` と呼ぶので、両席の
   盤面を混ぜるときは改名が要る。既存の実装(`hu_match::pool_of`、
   Python 側の `joker_maps` / `canonical_jokers`)を必ず再利用すること。
   自前で導出すると静かに壊れる。
3. **207次元 vs 623次元。** 供給側は `input_dim` だけで分岐する。623次元の
   カード並び順は Python 側の順序で、クレート内部の順序とは違う。
   「同等の」再実装は無言で入力を入れ替える。
4. **400サンプルの joint ブロックがエンコード費用のほぼ全部。** 訓練は400固定、
   供給は200で判定済み(champion はこの設定でゲートを通っている)。
5. **fl_ev は 2026-08-21 に動いた**(14: 5.28 → **6.57**)。これより古い
   ラベルは全部5.28で値付けされている。
   **測定を始めるなら fl_ev の sha を記録して凍結すること。**

   FL専用シミュレータは 2026-08-22 に完走した(`ai/tutor/fl_sim_driver.py`、
   結果は `D:/ofc_data/hu/flsim/prod1_20260822/fixed_point.json`)。
   **表はまだ差し替えていない。物差しが2つあると判明したため。**
   - シミュレータが測るのは **スタックなし raw**(打ち切りが起きない世界の連鎖価値)。
     `ai/config/fl_ev.json` の値は **in-game paid**(`method` フィールドが
     "paid settlements"、幅17の SE 3.58 が参照ランの paid SE 3.576 と一致する
     — raw なら 3.79 になる)。**この2つを引き算してはいけない。**
   - 幅17でこの罠を実際に踏んだ: raw 87.17 と出荷値 70.07 を並べて「+17点の補正」
     と報告したが、同じ物差しに直すと 72〜79 で **70.07 と区別できない**。
     内訳は truncation セマンティクスが +8、2026-08-19 の60kランが既に測っていた
     分が +5.7、固定点そのものは **+0.37 のみ**。
   - 確定した成果は3つ: **100点説の棄却**、幅17の SE 3.79 → 2.10、
     そして幅14の「8〜9へ収束」の否定(根拠だった縮小比0.63は別世代の測定を
     差分したもので、同一写像の比ではなかった)。
   - 構造的事実: ステイ可能な配置の royalty は必ず10以上、非ステイは最大27。
     したがって **fl_ev > 29 では `play_fl` の選択が表に依存しない**
     (`frontier.rs` に不変性テストあり)。幅16/17で表を動かしてもステイ率が
     1ビットも変わらないのはこれ。**周回差を精度と読まないこと。**

   **帰結: 表を凍結するときは sha だけでなく「どの物差しの値か」も記録する。**
6. **FLはミラー/deep-eval では打たれない**(entry 時に fl_ev で計上)。
   目的関数が `settle + fl_ev差` なので、微細な配置判定は fl_ev に敏感。
   実際に fl_ev(15) が 16.2 付近で首位が入れ替わる例が記録されている。

## 5. 訓練側(段D)は素通りできない

`ai/tutor/train_t4_first_evaluator.py` には:

* **warm start が無い**(`--init-from` / `--resume` に相当する引数が無い)
* **per-sample の重みが無い**(ルート内のランキング損失のみ)

レギュラー側の回転1は「現行から warm start + 誤りをK倍複製」で成立した。
ジョーカー側では:

* 過重は **`.npz` の行を複製する**ことで実現する(キーは `x, y, jokers, roots`)。
  `roots` が regret の集計単位なので、**ルートidの衝突を避ける**こと。
  既存の実例が `ai/tutor/verdict/build_union_fit.py`(連結時にidをずらす)。
* warm start は訓練スクリプトに手を入れるか、warm start 無しで受け入れるか。
  **無しの場合、回転1の再現性は落ちる**(あちらは前世代からの微調整だった)。

## 6. 着手前に片づけるべき衝突

1. **lap 3 が同じ機械を使う。** union 供給下での on-policy トレース → fl_ev 6.57
   での再ラベル、が既に宿題として積まれている。`--hu-trace`、GCSの run-id、
   `D:/ofc_data/hu/{street}_enc_{tag}` の命名まで一緒なので、
   **コーパスのタグと run-id を `onpol` / `lap2` / `t0l2` / `both` と重ならない
   ものにする。**
2. **fl_ev の固定点探索は完走したが、表はまだ変えていない**(§3-5)。
   採択は世代境界の判断であり、途中で表が変わると全ラベルの値付けが変わる。
   **現状は据え置き = 移植の作業中に表が動く恐れは低い。** ただし採択が
   起きるとしたら raw→in-game の換算を決める作業が先に入るので、
   その時点で凍結した sha が無効になる。
3. **ローカルCPUは現在レギュラー側の採掘で埋まっている。** ジョーカーの
   ロールアウトは rayon 並列でCPU律速なので、同時に回すと競合する。
4. GCP quota はレギュラー側と共有。

## 7. 推奨する段取り

```
0. fl_ev の現在値と sha を記録して凍結する
1. 較正: 1局面を deep_replay に通し、単価と扇と rollouts の効きを実測
2. ノイズ定数: 数局面で R本のロールアウト束の gap 散らばりを測る
   → 固定深度を決める。レギュラーの 8x256 は流用しない
3. 地図: 7マス x n=120 を on-policy 局面で測る(--hu-trace → extract_onpolicy_requests)
   判定は固定深度・EV加重(逐次peeking禁止)
4. 最漏れマスを別シード束で追試
5. フライホイール1回転: 採掘 → .npz行複製で過重再学習 → 清潔な検収 →
   1スロット差し替えのミラー判定 2シード束
   (対差分の集計スクリプトは書き直しが要る)
```

**供給フラグ(`--hu-topk 4 --serve-joint-samples 200`)を必ず付ける。**
忘れるとゲートを通った構成と別物を測ることになる。

### 判定基準は 4σ ではない

レギュラー側は経験的SEの4σで「確定誤り」を切ったが、**ジョーカー側の流儀は
2シード束以上でプールした95%ブートストラップCI**であり、σ表記は使わない。
移植時は向こうの流儀に合わせること。手法として本質的なのはσの数ではなく
「固定深度で1回だけ判定する」「複数シード束をプールする」の2点で、
ブートストラップCIはその両方を満たす。

閾値そのものも移植しない。レギュラーの 4σ は「候補を殺す不可逆な操作」に
張った閾値であり、ジョーカー側で同じ役割を果たすのは
「CIがゼロを除外するか」である。
